# Landing Page

Public Nodez marketing / download site. **v1 shipped in-app repo** as plain HTML/CSS.

Related: [[Distribution Versioning and Updates]], [[Product Roadmap]], [[Project Overview]], [[Agent and Human Setup]], [[Next Steps]]

## Placement (decided 2026-08-22)

| Choice | Detail |
| --- | --- |
| Location | Separate public repo `paulbrett/nodez` → `C:\Sites\nodez` |
| Stack | Single-page **plain HTML + CSS** (tiny JS only to soft-fill version from manifest) |
| Host | **Cloudflare**, serving `https://getnodez.app/` from the repo. *Not* GitHub Pages — see below |
| OTA | Manifest + bundles under landing repo `updates/` |

```text
nodez/          # github.com/paulbrett/nodez (public)
  index.html
  styles.css
  updates/
    latest.json
    bundles/
  .github/workflows/pages.yml
```

## Hosting correction (2026-08-25)

`.github/workflows/pages.yml` **fails on every push** and has since 2026-08-22:
`configure-pages` returns `HttpError: Not Found` because Pages is not enabled on
the repo. The site is live regardless, because **Cloudflare serves it** — pushing
to `main` is what deploys, and the Pages workflow contributes nothing.

Consequence: a red run appears after every landing push and can be ignored, which
is a bad habit to build. The workflow should either be deleted or Pages should be
enabled and the duplication resolved. Until then, verify a landing deploy by
curling the live URL, not by reading the Actions tab.

## Wiki (2026-08-25)

Public docs at `https://getnodez.app/wiki/`. Ten static pages, generated by
`scripts/build-wiki.mjs` in the app repo (`npm run wiki`), written into this
repo's `wiki/` plus a `wiki.css` that layers on the existing `styles.css` tokens.
Same landing-dir resolution as `publish-update-feed.mjs`, and the same principle:
no build step or runtime dependency is added to the static site.

**The wiki is not a mirror of this vault.** Adding a note here does not publish
it — a page has to be listed in the generator's manifest. Two guards enforce
that, and both caught real mistakes during the build:

| Guard | What it stops |
| --- | --- |
| Forbidden-pattern scan over rendered output | Home paths, Windows user paths, signing-key references, tokens, third-party project names |
| Frontmatter `type` allowlist | Roadmaps, backlogs, logs, agent contracts and research notes, whatever their titles promise |

**Pages are authored, not harvested.** Every doc in this vault turned out to be
an engineering spec once read closely, so `wiki-content/` in the app repo holds
nine pages written for a reader and derived from this vault's substance. The
vault-harvesting path still exists and is still guarded, but nothing uses it.

**`whats-new.md` does not track `CHANGELOG.md`.** That file is written for
developers; generating from it would reintroduce the language the wiki exists to
avoid. Update it by hand at release time, then `npm run wiki`.
